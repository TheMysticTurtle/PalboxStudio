# Palbox Studio — working notes

Palbox Studio is a desktop editor for the Palworld 1.0 **Global Palbox**. It reads
`GlobalPalStorage.sav` directly, shows every Pal in the box, and gives full, safe control over each
Pal's attributes through a native interface. It runs as a standalone application — it never modifies
the game, installs into Palworld, or writes into the game directory.

This file is the front door for anyone — a future session or a new contributor — picking the
project up. It points you at the deeper notes rather than repeating them, so start here and follow
the links.

## The non-negotiables

These four hold across every feature. Everything else is negotiable; these are not.

1. **Save safety comes first.** A Pal box represents real hours of someone's play. No edit is worth
   risking it. The write path is deliberately conservative (see *Save safety* below), and it is not
   loosened to make anything else easier.
2. **Scope is the Global Palbox, and only that.** Palbox Studio edits `GlobalPalStorage.sav`. It
   does **not** edit world saves, bases, party Pals, the map, or technology — even where the engine
   could technically reach further. Staying focused is what keeps the tool easy to trust, test, and
   support.
3. **The core is headless; the UI is a separate layer.** `core/` never depends on the UI, and the
   UI talks to it only through the Tauri command bridge. The engine must be usable from tests (and a
   future CLI) with no interface attached. The UI is meant to keep evolving, so adding or rearranging
   a panel should never require touching the engine.
4. **Official Palworld terminology throughout the UI.** Use the game's own names for stats, IVs,
   the Statue of Power level, passives, moves, and jobs — no fan slang. The app should read like an
   official companion tool.

## Architecture at a glance

- **`core/` (`palbox-core`)** — the headless Rust engine: the Palworld 1.0 save model, load/write,
  and every edit operation, with the verified 1.0 limits and unit tests that run against real save
  data.
- **`src-tauri/` (`palbox`)** — the Tauri 2 desktop shell. It owns the open-box session and marshals
  commands between the UI and the engine.
- **`ui/`** — the Svelte 5 + Vite frontend (SvelteKit static/SPA). The design source of truth is the
  prototype under `design/`; lift its values rather than re-deriving layout from notes.
- **`database/` + `data/`** — two clearly separated data planes: a **bundled, read-only** SQLite
  reference database (species, moves, passives, Partner Skills, ranch products, localization) loaded
  into memory at startup, and a **writable** user database for groups, tags, and presets. User
  metadata is keyed by each Pal's `InstanceId` and is never written into the save.

## Save safety — the rules that never bend

- **Never touch a live save.** All testing happens on scratchpad copies, never on the files under
  `%LOCALAPPDATA%\Pal\Saved\SaveGames\`. Point the engine's real-save test at a copy via the
  `PALBOX_TEST_SAV` environment variable.
- **Prove every edit path with the no-edit round-trip diff.** Load a box, save it, and diff it
  field-by-field against the original: the result must be **zero** fields added, removed, or
  changed. An edit path isn't trustworthy until an unmodified box round-trips byte-identical.
- **The write path, in order** (do not weaken any step to simplify packaging or anything else):
  1. Encode the edited box in memory, then **decode the generated bytes again** before the original
     is touched.
  2. Create a uniquely named backup in the save's sibling `PalboxStudio-backups/` folder, sync it,
     and verify it **byte-for-byte** against the source. Any failure removes the incomplete backup
     and **aborts** the save.
  3. Write to a sibling temp file, sync it, verify its bytes, and decode it again.
  4. **Atomically rename** the verified temp file over the original — no partial writes ever reach
     the target.
  5. Preserve the original compression / `save_type` so an unmodified box round-trips byte-identical.

## Build, run, test

Requirements: Rust (stable-msvc) and Node.

```bash
npm install && npm --prefix ui install   # one-time
npm run tauri dev                         # run the app with UI hot-reload
```

- `npm run build` — build the frontend (Tauri embeds `ui/build`; build it before `cargo build`).
- `npm run check` — Svelte/TypeScript type-check (expected: 0 errors / 0 warnings).
- `cargo test` — the engine tests. Set `PALBOX_TEST_SAV` to a **scratchpad copy** of a real
  `GlobalPalStorage.sav` to include the round-trip test; never point it at a live save.
- The reference database (`data/palbox-reference.db`) ships as a bundled resource. Its generation is
  maintainer tooling, currently being reworked into a self-owned data pipeline; the shipped app
  needs only the bundled DB.

To produce the installer and portable zip:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/build-release.ps1
```

## Working discipline

- **One feature per branch**, branched from current `main`, with self-contained, PR-quality commits.
- **Commit messages explain the *why* (the problem or motivation), the *what* (the concrete
  change), and the *test results* (what was run and the outcome)** — not terse one-liners.
- **ADRs for anything architectural**, kept in `docs/decisions/`.
- Best practice, no corners cut. Comment the code, fix genuinely out-of-place things when you're
  already touching them, and leave the whole project coherent — not just the one task closed.
- Keep `docs/PROGRESS.md` current so the next session can pick up cleanly.
